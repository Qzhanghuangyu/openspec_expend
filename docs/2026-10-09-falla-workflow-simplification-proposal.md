## 1. 修改目标与已确认边界

把主要精力放到“需求是否分析清楚、是否拆到可判断的行为”，减少普通 Android 开发中重复的规则阅读和记录负担。保留官方 OpenSpec 内核，不迁回 Mercury 的命令实现。

已确认的边界：

- **不调整 Apply 停顿频率。** 每轮仍只推进一个 task，完成并落盘后汇报，用户在同一 Apply 会话回复“继续”才进入下一轮。
- Preflight、Propose、Apply、Archive 的阶段发起和授权规则保持现状。
- 本文不是正式需求批准记录，不创建 OpenSpec change，也不自动启动实施。

建议分两步推进：第一步改善 Preflight 和后续规划的需求覆盖；第二步再精简 single 模式的规则阅读及交接展示。第一步不改变现有 Schema DAG、comate 格式、认领锁或基线协议。

## 2. 当前问题及原因

| 当前表现 | 对应原因 | 建议方向 |
| --- | --- | --- |
| 整个页面或功能只列成一个需求项 | Preflight 模板未定义一行需求的粒度 | 按独立行为分别列项，逐项判断实现状态 |
| 明显主干能发现，状态迁移与必要边界容易漏 | 有“不要机械枚举”的限制，缺少正向覆盖步骤 | 先找需求内真实对象、事件、状态，再检查适用维度 |
| 多个待确认决定合成一个大问题 | 未要求问题可独立答复 | 一个问题对应一个决定，关联受影响行为 |
| Preflight 较粗，Propose 沿用粗结论 | 后续要求复用证据，但未要求反查需求覆盖 | 将细分行为映射到规格与任务，发现缺口回到对应阶段 |
| 普通开发阅读、填写的内容较多 | single 和 parallel 的细则在同一长文档，handoff 字段较多 | 明确适用条件，交接记录围绕当前任务增量更新 |

依据：当前 Preflight 第 5–6 步强调主干、硬冲突和必要边界；实现状态表只有“需求项、状态、证据”；完成标准和准入程序均未检查独立行为的覆盖。Mercury 则明确要求对每个状态交互核对触发、迁移、来源和持久化。

“需求拆细”与“开发任务拆细”分别处理：Preflight 拆用户可观察行为；Propose 再按实现依赖形成任务。同一任务可以覆盖多个行为，同一行为也可能需要多个任务，不强制一一对应。

## 3. 第一步：改善 Preflight 的拆分质量

### 3.1 先拆行为，再调查实现

建议新增确定的分析顺序：

1. 读取完整 PRD 及适用评论，确定当前 Android 范围。
2. 按页面、区域或业务对象组织需求，再拆出各自的独立行为。
3. 为每个行为记录触发条件、可观察结果、需求依据和实现状态。
4. 调查相关源码、接口、模型及测试，给每项结论补证据。
5. 针对实际存在的状态、事件和接口检查必要缺口，分别记录待确认问题。
6. 反查 PRD，确认当前范围内的明确行为均已覆盖，然后维护现有 Blocker 台账。

拆分规则：

- 一条需求应能单独回答“要求什么、现在是否实现、如何判断”。
- 同一功能中，触发条件、结果或实现状态不同的行为分开记录；不能用“部分实现”笼统覆盖整页。
- “页面展示、默认选中、点击提交、成功反馈、失败反馈”等有独立需求依据时分别分析。
- 不按代码行、XML 属性或装饰图层拆项；不为增加条数拆出没有独立意义的内容。
- 已有关联实现但未核实关键分支时写“无法判断”并说明缺口；不得仅因搜索不到就断言不存在。
- 建议用本 change 内稳定的 `R1`、`R2` 等编号关联分析条目；它们只用于正文追踪，不替代 tasks 的章节.序号，也不新增独立台账文件。

### 3.2 按需求事实检查适用维度

保留“有界分析、不自行补产品决定”，把分析维度写成可执行的正向要求：

| 适用维度 | 需要核对什么 | 触发依据 |
| --- | --- | --- |
| 展示与入口 | 可见条件、内容来源、初始或默认状态 | PRD 明确的页面、区域或入口 |
| 状态与交互 | 事件、前后状态、状态来源、适用的持久化要求 | 实际存在的状态对象或交互 |
| 数据与接口 | 业务概念与字段、接口、错误码的映射 | 本次行为所需的数据契约 |
| 边界与异常 | 限制、并发或重复操作、失败等是否影响验收 | PRD、接口契约、平台硬约束或当前实现路径 |
| 兼容与生命周期 | 与旧行为是否冲突，资源和回调由谁持有 | 受影响代码及已核实的工程约束 |

这些维度用于检查覆盖，不要求每个功能都写五段。不涉及权限就不加权限问题，没有提交就不加重复提交问题。已明确且已核实的内容保留简洁结论，不反复提问。

区分发现缺口与选择方案：可以指出“异步提交期间允许返回，但未定义返回后如何反馈结果”；不能自行规定取消请求、后台重试或弹窗策略。页面销毁后不能继续更新已销毁 View 是工程约束；离页后业务请求是否继续可能是产品决定，二者分别记录。

### 3.3 输出结构建议

保留当前 YAML frontmatter、取证文件及问题类型，主要调整正文：

| 部分 | 建议内容 |
| --- | --- |
| 范围与来源 | 当前 Android 范围、PRD 及评论有效结论 |
| 需求行为差分 | 编号、页面/对象、独立行为、触发与结果、需求依据、实现状态及证据 |
| 待确认问题 | 问题编号、关联行为、缺少的单一决定、影响、类型、级别 |
| 覆盖核对 | 未覆盖或无法判断的项，以及明确排除的范围 |
| 结论 | 当前差分、待确认决定、Blocker 和下一阶段条件 |

主表优先易读。触发条件或证据较长时放在条目下，不强行塞进很宽的表格。范围外内容只做简要定位，不重复生成其他端的完整需求分析。

一个问题对应一个可独立答复的决定。不同决定分开记录；多个行为共享同一个决定时可以关联多个编号，不复制问题。Blocker 沿用现有 `B1` 等编号，正文直接引用；普通问题可使用 `Q1` 等编号，不建立第二份决定状态台账。

### 3.4 前后示例

以下为合成示例，不代表已有产品需求：PRD 要求显示奖励、满足条件后可领取、提交成功显示编号，并允许在提交期间返回；接口已证实不支持幂等，重复点击和离页后的业务行为未定义。

粗粒度写法：

| 需求项 | 状态 | 说明 |
| --- | --- | --- |
| 奖励领取页面 | 部分实现 | 已有展示，领取流程需完善 |

建议写法：

| 编号 | 独立行为 | 状态示例 | 差分或待确认项 |
| --- | --- | --- | --- |
| R1 | 显示奖励内容 | 已实现 | 有对应绑定与数据证据 |
| R2 | 按条件显示领取入口 | 部分实现 | 已有按钮，领取条件来源未接通 |
| R3 | 点击后提交领取请求 | 未实现 | 当前入口无请求调用 |
| R4 | 成功后显示编号 | 未实现 | 返回模型未映射到显示区域 |
| R5 | 提交期间再次点击 | 无法判断 | 非幂等接口下，是否允许再次提交待确认 |
| R6 | 提交期间离开页面 | 无法判断 | 业务是否继续及结果反馈方式待确认；另核对回调所有权 |

R5、R6 的触发场景已存在，但行为未定义，不能当作已确认规格。问题分别记录，是否为 Blocker 根据其实际阻断的规格、设计或实施决定判断，不因为属于边界就统一升级。

### 3.5 与 Propose 的衔接

- proposal 仍按业务能力组织，不把每个 R 编号变成一个 capability。
- specs 引用已确认行为并形成可测试场景；合法 `skip_specs` 时说明行为在 design/tasks 中的承接。
- design/tasks 使用简短的“覆盖：R2、R3”等正文引用表达责任，保持现有任务编号和依赖格式。
- 反查每项行为是否已实现无需改动、由具体任务覆盖、仍待确认或已明确排除；不得无声遗漏。
- 多项行为可合并成一个边界清晰的开发任务，不要求每个控件或每个行为单独一个 task。
- 缺少产品决定回 Preflight，已确认行为的方案或任务缺口留在 Propose；不重复分析完整 PRD。
- Apply 仍一次一个 task，行为拆分不增加阶段发起权限。

第一步不新增需求覆盖解析器。程序继续检查现有格式与准入，语义覆盖由 Agent 核对、人工审阅；文档必须明确这一限制。

## 4. 第二步：精简日常记录与规则阅读

这部分在第一步验证有效后再实施，避免同时改动分析和协作协议。

### 4.1 single 优先读取适用规则

建议在 coordination 文档中给出清晰的适用入口：通用完成/验证规则、single 执行规则、parallel 协调规则、发生实质变更时的基线复核规则。

普通 single 无子映射、无跨 change 依赖时，不需要理解全部父协调者交接和子节点恢复示例。存在跨 change 依赖、旧记录或基线变化时仍加载相关章节，不能因为 single 就忽略这些约束。

先改善章节导航和适用条件，不新增一套轻量/严格 profile，不复制出第二套规则，不新增配置开关。

### 4.2 handoff 增量更新

建议保持一个 handoff，围绕当前 task 更新“完成了什么、改了什么、验证结果、下一步和风险”。

- 已确认且未变化的事实、设计和项目规则结论，引用原有位置，避免每轮复制全文。
- 注释审计仅覆盖本 task 新增或实质修改的符号，不重复审计之前未变化的文件。
- 生命周期收尾按现有规划节点执行，普通 task 只记录自身引入的相关风险，不每轮重写整页检查。
- 人工验收仍只记录对应任务及结果，失败定位信息按需补充，不要求上传截图或过程材料。
- 运行命令、variant/设备、结果与限制保留必要信息，未运行不写通过。

**不直接删除机器依赖字段。** 当前 done 校验要求 handoff 中的完成、注释审计、验证、安全及风险内容。先通过精简示例和增量记录改善填写体验；如果仍需要改变字段结构，另做格式兼容设计及行为测试。

### 4.3 当前建议保留的能力

| 能力 | 本轮建议 |
| --- | --- |
| 官方 OpenSpec、自定义两套 schema、标准 openspec 目录 | 保留 |
| single/parallel、comate、认领和项目锁 | 保留，暂不改状态协议 |
| 基线与影响回退 | 保留；实质变化仍复核，不能刷新 hash 追认旧进度 |
| 每个 task 完成后的校验及暂停 | 保留，不降低频率 |
| 安装防覆盖、路径及符号链接检查 | 保留 |
| Android 生命周期、安全、必要构建与人工验收 | 保留 |
| CodeGraph、Figma、UI Knowledge | 按现有适用条件启用，不变成每项需求固定步骤 |
| PRD 评论取证与版本核对 | 保留来源完整性要求；展示只留必要结论 |

此前讨论过移除 single 的 comate、认领或基线，本方案暂不采用：它们已经被 schema、校验、恢复和归档共同消费，一次移除会扩大改动及迁移成本。

## 6. 验证方式与验收条件

第一步用同一份合成 PRD 对比修改前后，并在输入和可用源码证据相同的条件下检查：

- 明确行为是否全部被覆盖，是否仍把实现状态不同的行为合在一项。
- 是否发现有范围依据的必要状态或边界缺口，问题能否独立答复。
- 是否产生无关权限、弱网、缓存等通用问题，是否自行选择未确认方案。
- 每个状态结论是否有具体证据或明确的核验缺口。
- Propose 是否能承接各行为，同时避免“一行为一任务”的机械拆分。

至少覆盖：简单静态展示、已有页面新增交互、异步非幂等提交、已有功能差分、带评论澄清的 PRD。条目数量只作观察，不作为合格阈值；简单需求允许很少条目。

必要的格式和路由测试只验证结构契约，不宣称能够证明自然语言分析质量。模型采样属于人工评估证据，注明输入、条件与局限，不能把一次输出当稳定保证。

实施后运行与修改相关的模板、规则及 Schema 契约测试。若改到协作字段或解析器，再运行认领、完成、基线及归档的行为回归；本方案不涉及 Android 业务代码，不需要构建 Android 应用。初稿阶段未重跑测试；第一步实施后的结果和局限见文首验证记录。

验收底线：Apply 仍每轮一个 task 并等待“继续”；既有 Blocker 准入、任务依赖、人工结果、基线和安全写入门禁没有被削弱。

## 7. 兼容、更新及回退

- 第一阶段不新增 schema、不改变 artifact ID 或依赖关系、不提升 comate 格式版本。
- 旧 preflight 不自动重写，不因缺少新行为编号就把既有进度判为无效。续做时根据实际需求变化补证据，已有完成证据遵循现有影响复核协议。
- 已开始的 tasks 不批量改编号；新覆盖引用仅在必要时由 Propose 更新，不靠改排版刷新基线。
- 已归档记录保持原样，需要新增或修订行为时使用新 change。
- 包模板更新不会自动更新目标 Android 项目中的安装副本；按现有 install/doctor 流程更新并重开 Agent 会话。用户修改过的受管文件仍显式报冲突，不强行覆盖。
- 回退恢复对应版本的规则和模板，不自动删除新生成的需求条目或回滚已完成业务代码。已产生的需求决定和人工结果分别核实保留。

## 8. 潜在风险

| 风险 | 控制方式 |
| --- | --- |
| 需求过度拆分，条目和提问膨胀 | 以独立判断和验收为边界，不按控件数或固定条数验收 |
| 将必要边界补成新产品要求 | 明确区分已确认行为与待确认决定，保留范围依据 |
| 所有问题都升级为 Blocker | 根据实际阻断的下游决定定级，Major/Minor 继续记录 |
| 覆盖编号变成新的复杂协议 | 先仅作 Markdown 引用，不新增独立台账和解析器 |
| 简短 handoff 丢失完成证据 | 保留现有必需字段和真实验证结论，增量更新不等于省略验证 |
| 精简阅读后漏掉跨 change 或旧记录限制 | 按实际依赖、模式、基线状态触发对应章节 |
| 模板更新造成旧进度失效 | 不自动重写旧记录，实质变更按影响范围复核 |
| 细分证据泄露 PRD、业务数据或凭据 | 只保存必要的脱敏结论和项目内证据定位，不复制原文、token 或临时链接 |
| 生命周期风险在交接精简中被遗漏 | 保留代码收尾与必要运行验证，区分业务决定和资源所有权 |

## 9. 建议采纳顺序
