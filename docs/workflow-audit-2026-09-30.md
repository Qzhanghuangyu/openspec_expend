- 每个归档目标先用 `coordination resolve` 获取官方物理名，再执行 `coordination preflight <change> --json`；成功返回的 `parent` 用于 `coordination validate --change <parent> --json`，不从命名猜父子关系。两条 Falla 门禁都要求退出码 0 且 `ok: true`；失败、缺失或无效结果停止，不执行官方归档。

### W04：parallel 父协调职责与状态闭环

- 父在用户明确进入协调回合后通过 `coordination claim <parent> --coordinator --owner <id>` 排他认领；默认模板仍为 unassigned/todo，不在 Propose 自动分配或启动实施。复用项目协调锁、官方规划、Preflight、父 DAG、上游完成及实施基线门禁，首次初始化只写本父 owner/status/baseline；同 owner 重试重新检查。
- 子实施独立认领，不因父协调身份获得子代码/任务写权限；父须是已分配 owner 的 in-progress。未认领父的合法规划仍可保存，子列为 blocked 而非 ready；已有子进度而父责任缺失由 validate/doctor 报错，不能默默保留错误关系。
- 新增 `coordination transition <parent> --owner <id> --status blocked|in-progress|done`。父 owner 先写暂停范围与恢复条件，安全暂停允许在基线/依赖失效时先阻断新执行；只更新父，活动子须由各 owner 分别暂停，未受影响的有效 done 子保留。恢复/done 在锁内验证候选状态、父里程碑、子完成、handoff、人工验收与最新基线，不自动勾任务、通过人工验收、刷新基线或修改子记录。
- 新增 `coordination transfer <parent> --owner <current> --to <next>`：原父 owner 先在 handoff 记录用户交接确认依据与接手操作；锁内仅替换父 owner，保持状态、任务、基线、人工验收和子记录。允许接手失效证据的恢复，不追认完成；候选者不可抢占，原会话不可参与时须人工核实后处理，不提供 force/超时自动接管。
- 父协调者负责父里程碑、总体验收、任务组暂停/恢复、父 done 及用户授权后的最终归档；权威 coordination、阶段规则、Skill、Schema、默认模板和 README 同步说明，不另建身份/状态事实源，不替代 W03 官方归档。
- 独立审查复现父认领在 owner/status 替换后超过 256 KiB 时先写后报错；新增失败回归后将最终 comate 结构/大小校验前移到落盘前，保持失败不改父子文件。旧无父身份与子旧证据场景可按安全恢复顺序解决，不放宽准入或基线门禁，已固化定向回归。
- 新写命令复用限量普通文件读取及原子文件替换；落盘前检查更新后的记录结构/大小、父文件 hash，以及恢复/完成期间读取的映射/父子任务与协作记录摘要，拒绝已检测到的并发修订。所有句柄与锁按 finally 释放；结果不返回负责人、交接确认或 handoff 正文。

### W05：逐人工任务结果与勾选一致

**用户确认的范围**：人工验收只需要明确结果，不要求程序验证验收真实性，也不强制截图、反馈正文、过程材料或逐项验收指纹。原始审计中的“逐项证据/基线”建议已收窄，以下实现为准。

- 父子 `comate.md` 保留 format-version: 2，新增 `human-task-results`，默认 `[]`；每项只保存 `[任务编号,结果]`，结果为 pending/passed/failed。例如 `[["1.1","passed"],["1.3","pending"]]`。使用数组避免 JSON 对象重复编号被静默覆盖；拒绝重复编号、未知结果和额外材料字段，诊断不回显原始输入。
- 已勾选的每项人工 task 必须有本项 passed，不等整个 change done 才检查。`human` 模式的全部任务都按人工处理；hybrid 只对 `[人工]` task 要求结果。`validate`、doctor、首次/同 owner claim、依赖交付校验、基线记录及父 transition 复用同一一致性门禁。
- 允许部分人工任务通过、其余待验收，总 human-review 可保持 pending；合法已通过项及其已满足的任务后继不因此失效。没有结果却勾选、结果 pending/failed 或错误关联都不能成为有效前置；含此类错误的父 DAG 不报告子 ready，须先修复当前失效记录。
- 移除原 done 时强制“人工验证反馈正文”的校验；只有编号和通过结果即可，原 handoff 反馈保留为可选备注。UI 视觉的人工对照仍由人工执行，但仅需给出通过/不通过，页面、设备和差异按需补充，不索要截图或验收材料。Agent 构建/测试、注释和资源生命周期等既有工程门禁保持不变。
- 人工结果变化不影响实施基线 fingerprint；需求/设计或完成条件变化仍使用 W02 的当前基线与 affected/preserved 复核。受影响的人工 task 先回退 checkbox、总人工状态与本项 passed，其他有依据的通过项保留。旧无快照但已有逐项 passed 视为旧验收结果，不能直接初始化追认；不另建逐项基线或证据来源。
- 人工进度保留原逐 checkbox 的续行/嵌套归属，仅与任务图共用显式编号读取；基线正文扫描单独保留，不用正文合并推导人工属性。参与人工结果关联的编号在全部进度项中检查唯一性，含旧围栏，歧义不能由一个 passed 支撑多项验收。保留官方 checkbox 数量及旧围栏中的显式编号，代码示例人工标记不扩散到外层。缺字段旧记录仍可读取，但总 passed、旧勾选或笼统反馈不自动转换为逐项通过；已勾选的未编号人工 task 需由 Propose 显式核对编号和引用，不自动重编。失败校验不写 owner/status、任务或其他记录。
- 独立审查发现初版复用基线正文扫描会丢失旧围栏中的人工续行/编号，并把嵌套代码示例的人工标记扩散给外层普通任务；三类问题均先固化失败单测，再分离人工归属和基线正文扫描修复。新增真实旧记录回归确认 DAG/health 不错误放行、仅补本项结果即可恢复、不误阻断普通任务，且不修改原任务和既有基线。
- 复审补充两项关联边界：人工进度与基线正文归属不同时，affected 编号仍不得保留旧 passed，人工总状态回退使用真实进度归属；正文与旧围栏同编号参与验收时拒绝歧义，不让结果复用或 Map 覆盖。均有失败/修复后的单测及真实 CLI 回归，快照语义和普通旧示例进度不变。
- 回归覆盖缺结果误勾、结果 pending/failed、合法部分通过、结果撤销的局部回退、父子独立人工结果、旧笼统反馈补核验、未知/重复/超预算/额外字段、脱敏错误、旧围栏解析及人工归属/编号歧义。**17 项结果单测、11 项真实 CLI 流程、3 项基线回退回归**已通过；使用真实 OpenSpec **1.12.0**，没有用永远 ready 的 status stub。审查修复后 `npm run check`、`npm test` 通过：**375 项通过，0 失败、0 跳过**，约 66.1 秒；独立复审确认上述五项发现已修复，限定范围内未发现剩余可复现阻断；文档及补丁检查通过。

**兼容与风险**：旧人工结果需要按任务补关联，不能由 Agent 从“都通过了”或 checkbox 自动推断；旧未编号任务只显式核实，不批量重写进度。程序只能检查编号、结果和当前记录一致，不能识别人工虚填的 passed。结果撤销不会自动改写任务/兄弟记录或终止已运行 Agent，需原 owner 按协作协议暂停、局部回退。旧归档依赖缺少可核实的逐项结果可能阻断，继续按 W01/W02 新 change 处理，不原地改归档。本地锁不覆盖直接文件编辑与跨机器协作。无 Android 业务代码改动，未进行真机泄漏或生命周期验证；按用户要求单独本地提交，不推送。

### W01：不能以 preflight 文件完成代替阻塞问题已解决

**位置**

- `templates/skill-spec/[分析必读]preflight.md:54-68`：记录 Blocker，同时要求写文件后检查 artifact done。
- `templates/skill-spec/[架构必读]propose.md:15-18,68-77`：入口主要检查官方 preflight 完成，没有显式逐项检查未关闭 Blocker 的准入步骤。
- `templates/skills/falla-propose/SKILL.md`：同样以官方状态作为起点。
- `src/coordination/claim.js:91-97`：检查 `isPlanningComplete`，不读取需求阻塞决策。

**触发场景与复现**

在临时 change 的 `preflight.md` 中明确写入“Missing Definition / Blocker / 待用户确认 / 阻断 proposal”，其他规划文件存在且格式可被接受。真实 OpenSpec 1.12.0 与协调命令返回：

```text
status.isPlanningComplete = true
instructions apply.state = ready
coordination validate.ok = true
coordination claim.claimed = true
```

官方 artifact 完成状态不是需求澄清状态。当前 Soul 的禁止猜测规则仍然有效，但若 Agent 或人工漏检 Blocker，后续程序门禁无法兜底。

**建议修改**

1. Propose 明确检查当前范围内每个 Blocker 的结论与用户确认依据；“调用 Propose”不能视为默认接受未决需求。
2. 在 preflight 内定义最小结构化决策字段，例如问题 ID、影响范围、未决/已确认/明确排除、确认依据。不要另建重复事实源。
3. Falla 校验/认领检查相关未决阻塞项；缺字段的旧 change 报告“未核验”，不自动当成零阻塞。
4. 非阻塞事项允许继续调查和独立规划，但不得在 spec/task 中自行填入依赖该决定的行为。

**潜在风险**：不确认的默认值、文案、接口语义或异常处理可能被固化成规格与代码。

**建议回归**：Blocker 未解决时拒绝相关准入；有明确决定后才放行；不受该问题影响的范围按明确政策处理。

### W02：需求/设计修订没有统一的完成证据失效协议

**位置**

- `templates/skill-spec/references/coordination.md:56-66`：已规定构建或运行证据推翻完成任务后的回退。
- 同文件 `:82`：代码、资源、配置、环境变化后人工验证退回 pending。
- `templates/skill-spec/[架构必读]propose.md:79`：允许用户审阅或修改 design/tasks。
- `templates/skill-spec/[模块选读]apply.md`：允许返回 Propose，但没有完整定义重规划对已有进度的失效处理。
- `src/coordination/comate.js:211-250`：校验任务数与记录字段，没有关联验收基线版本。

**触发场景与复现**

一个未归档 change 已完成任务并标记 done；随后修改 `design.md`，明确改变验收基线，保留旧 checkbox/comate。结果仍为：

```text
instructions apply.state = all_done
coordination validate.ok = true
```

这不要求内容校验器理解所有自然语言，而是说明目前连“完成证据对应哪一版设计/完成条件”都没有稳定关联。设计源差异已有返回 Propose 的规则，但返回后如何撤销旧进度仍不完整。

**建议修改**

1. 将 PRD 已确认决定、spec、design、task 完成条件的实质变更纳入现有回退协议。
2. 重规划先列受影响任务、依赖和验收项；保留不受影响进度，撤销失效 checkbox/人工验收，并更新父子状态。
3. 用基线指纹或显式修订号关联完成证据。变更首先触发“需复核”，不要因纯排版修改自动清空所有进度。
4. 明确 Apply 发现需求本身变化时，哪些情况先回 Preflight、哪些仅需 Propose 修订；已归档内容继续走新 change。

**潜在风险**：旧版本验证结果被用来证明新版本需求完成；已通过的生命周期或人工验收证据可能不再适用。

**建议回归**：实施中/已完成/parallel 下游三种状态下修改基线，均不能静默保持旧完成结论。

### W03：single 归档遗漏协调门禁

**位置**

- `templates/skill-spec/[任务选读]archive.md:25-30`。
- `templates/skills/falla-archive-change/SKILL.md:31-40`。

两处都仅明确要求 parallel 父 change 运行 `coordination validate`。single 虽要求人工/Agent 核对 comate，但未强制复用现有机器校验。

**触发场景与复现**

临时 single change 的任务均勾选，但任务 `1.1` 引用不存在的依赖 `9.9`：

```text
coordination validate.ok = false
error.kind = task-dependency-missing
openspec validate --strict：passed = 1, failed = 0
openspec archive --yes：成功归档
```

该复现仅归档临时合成数据。官方 OpenSpec 不负责 Falla 的本地任务依赖和 handoff 协议，不能用官方 strict validate 替代协调校验。

**建议修改**

- 所有模式归档前均加载 coordination 完成门禁并执行相应父 change 的协调校验。
- 逻辑子 change 也应在归档前检查相关父 DAG，避免先归档错误子记录、再到父归档才发现问题。
- 区分用户明确接受的未完成告警与记录结构/依赖错误；对后者修正记录，不能默认为官方 `--no-validate` 一并豁免。

**潜在风险**：非法进度被封存；后续跨 change 依赖继续读取无效归档记录，恢复成本增加。

**建议回归**：single 和 parallel 子/父归档都覆盖任务依赖错误、人工证据缺失及父子状态冲突。

### W04：parallel 父协调者的身份与状态流转未闭合

**位置**

- `templates/skill-spec/references/coordination.md:27`：要求通过 claim 认领。
- 同文件 `:59-69`：要求父 owner 更新父状态，子执行者只修改自己的子记录。
- `templates/skill-spec/[架构必读]propose.md:56-57`：父 tasks 保存协调里程碑。
- `src/coordination/claim.js:107-110`：拒绝 parallel 父认领。
- 父 comate 模板默认 `owner: unassigned`、`status: todo`。

**触发场景与复现**

创建合法 parallel 父与子 change。认领父返回“parallel 父 change 必须认领逻辑子 change”；认领子成功。父里程碑、总体验收和状态回退仍需有人负责，但规则没有定义该负责人怎样产生、如何排他接管。

这不是说父状态完全不能手工修改，而是现有规范没有交代手工指定父 owner 是否为被允许的例外、由谁执行、如何防止并发覆盖。

**建议修改**

- 明确区分“父协调责任”和“子代码实施责任”。
- 提供父协调者认领方式，或在 Propose 明确指定父 owner 并定义合法接管、锁定和恢复机制。
- 指定谁推进父里程碑、汇总人工验收、设父 done、发起归档；父协调权不自动授予修改子代码的权限。

**潜在风险**：所有子任务完成后父 change 仍停在 todo；多个执行者手动修改父记录；上游失效时无法可靠暂停整个任务组。

**建议回归**：从默认模板开始跑完整 parallel 流程，不在测试夹具里直接预填父负责人，验证父认领到归档的闭环。

### W05：人工任务的反馈校验晚于任务依赖解锁

> 以下为原始审计发现；用户后续确认只需要逐任务结果与勾选一致，不强制反馈材料或逐项验收基线，实际修复见上方 W05 进度。

**位置**

- `templates/skill-spec/references/coordination.md:77-82`：人工任务只可凭明确反馈勾选。
- `src/coordination/comate.js:174-207`：只统计人工任务总数，没有保留逐任务验收结果。
- 同文件 `:231-246`：人工状态/反馈门禁主要在整个 change 为 done 时检查。

**触发场景与复现**

```text
status = in-progress
validation-mode = hybrid
human-review = pending
人工验证反馈为空
[x] 1.1 [人工] 人工确认（依赖：无）
[ ] 1.2 后续交付（依赖：1.1）
```

`coordination validate.ok = true`，同 owner 再次 claim 也成功。误勾的人工 task 已满足本地任务依赖，可导致后续任务被选中；最后 change done 时才可能被拦截。

**建议修改**

- 对已勾选的每个人工 task，要求可定位的人工反馈及对应验收基线；在检查点和依赖解锁时校验。
- 允许部分人工任务通过、其余 pending。不能简单规定“总 human-review 是 pending 就禁止所有已完成人工任务”。
- 人工反馈撤销或相关基线改变时，只撤销受影响任务并阻断其下游。

**潜在风险**：人工未确认的结果提前成为其他任务的输入；后续实施建立在无效验收之上。

**建议回归**：空反馈误勾必须失败；有反馈的部分验收应能通过；其余未验收项仍阻塞对应下游。

### W06：应区分“不编造边界行为”和“不发现边界缺口”

**位置**：`templates/skill-spec/[分析必读]preflight.md:45-46`。

当前限定“只核对方法主干”“只有 PRD 明确要求或源码已证实的问题才记录”，并禁止按状态交互及异常边界枚举。这有助于控制审查范围，但对新增功能，源码不存在，PRD 没定义的必要决定恰好也不符合这两类证据条件。

例如当前范围中确实存在异步提交，但取消后是否继续、重复提交是否被允许会改变验收口径；如果文档未写，应该记录为待确认，而不是自行设定处理策略，也不应该因为“不要枚举边界”而漏掉该问题。

**建议修改**

- 保留“不套通用清单、不无限枚举”的约束。
- 允许基于当前需求、接口契约、明确的平台约束或当前实现路径，识别会影响本次完成条件的必要边界。
- 发现缺口时只列触发条件、缺少的决定、影响和待确认项，不自行决定默认值、重试、兜底、弹窗或降级方案。
- Android 资源所有权、页面销毁后回调等可核实的工程约束照常处理；不把不确定的产品行为当成工程惯例。

**潜在风险**：正常路径看似明确，但异常/恢复路径到 Apply 才暴露，增加返工；或者 Agent 在实施时用“常规做法”补需求。

此项为规则设计建议，不声称已经发生真实需求漏检。

### W07：为“需要确认”与“可自行选择”给出最小判断准则

**位置**：Soul 第 5 节、Preflight 评论决策规则，以及 preflight/prd-source 模板。

目前已有禁止猜测、评论不自动覆盖正文等原则，但尚未统一定义哪些决定只能由用户确认、什么证据足以记录为“已确认”，以及非阻塞问题到哪个阶段必须解决。

**建议增加一张简短判断表**

| 情况 | 建议处理 |
| --- | --- |
| 当前源码/API/规格能核实的事实 | 记录证据，不反复询问 |
| 不改变业务行为且符合已确认约束的技术选择 | Agent 选择并说明重要取舍 |
| 改变业务行为、默认值、交互、服务端契约或验收标准 | 列问题及选项，等待明确决定 |
| 用户、PRD、设计、评论之间存在冲突 | 指明冲突及影响；只暂停依赖该决定的工作 |
| 范围外或当前阶段非阻塞的问题 | 记录为延后/排除，并写清何时需要解决；不能悄悄变成默认行为 |

每条关键决定最少记录“决定内容、确认依据、适用范围、被替代的旧结论”。无需保存完整对话或个人信息。不要把“文档缺省”“评论已解决”“用户未回复”当成同意。

**潜在风险**：一端是擅自补需求，另一端是对不影响业务的技术细节反复提问，导致流程过度停顿。

## 三、有意设置的限制，不应直接判成缺陷

- 每个任务后等待继续、阶段分别发起：当前 Soul 明确如此，属于执行策略。是否改为授权范围内连续执行需要产品选择。
- Figma 不默认读取截图、子节点导出另行确认：属于当前明确的数据访问和视觉验收策略，不能在审查中擅自放宽。
- 不每次构建：现有规则使用轻量检查加集成节点，与当前仓库使用要求一致。缺少集成验证证据时仍不得宣称构建通过。
- CodeGraph 失败允许有界降级：现有规则明确不能把文本命中当调用关系，属于有边界的降级。
- 旧任务格式兼容：当前有明确兼容政策，不建议为修新门禁直接强制重写所有存量进度。
