# Android 实现质量与范围

## 何时读取

Propose 定义实现约束或 Apply 修改 Android 代码、资源和配置时读取。

## 最小范围

- 只修改当前需求和当前 task 必需的文件、符号、资源与测试。
- 不顺带清理、重构、抽象、重命名、迁移、升级依赖、替换架构、统一格式或修复既有告警。
- 只能直接修复当前改动造成的编译、测试、安全或生命周期问题。
- 必须扩大范围时，先说明原因、影响和验证方式，并返回 propose 更新 design/tasks 或请求用户确认。
- 修改入口时只核对既有回调的受影响路径；未证实的旧问题不顺手加入销毁标记或声明已解决。

## Android 实现质量

- 遵循项目已有 Kotlin/Java/Android XML 格式；只格式化当前 task 触及的文件。
- XML 声明独占一行、属性逐行、子节点按层级缩进，禁止把复杂标签压成单行。
- 新增或实质修改的页面、组件、ViewModel、核心类和公共入口说明职责、边界和生命周期所有者。
- 新增或实质修改的公共/受保护方法使用 KDoc/JavaDoc；私有方法若包含业务分支、状态转换、
  异步/线程、资源所有权或非显然副作用，也要说明目的和关键原因。参数的业务含义、单位/范围、
  可空性、所有权或回调时机不明显时写清，必要时说明返回值、异常和线程。
- 状态字段、资源所有者、回调抑制标记和非直观常量说明用途；复杂 Lambda 提取为命名方法或说明参数。
- 方法短不等于简单。只有无分支、无副作用、无生命周期/资源语义的纯转发 override、getter、setter
  或委托才可豁免；生命周期回调、事件处理和状态/异步方法不能仅凭行数豁免。
  注释要说明已核实的职责与“为什么”，不重复代码字面意思，不把抑制迟到回调写成取消请求或证明无泄漏，
  也不把敏感数据写进注释。
- 每个 task 完成前对本次新增/实质修改的符号逐项核对：需要注释的已补齐，豁免的写明符号和理由；
  不得用“都是简单方法”概括整批改动。记录到 handoff 的“注释审计”，缺项不得勾选 task。
- 检查空值、异常、并发、异步取消、观察者/监听器释放、页面销毁后 UI 更新和敏感日志。
- 每项任务须可验证，不默认新增单测；纯状态转换、排序、默认选中等易回归逻辑，在项目已有测试基础时
  优先安排少量定向测试。日常任务先用轻量检查；资源打包、模块编译和应用构建按规划的集成节点执行。
  退出清理先静态核对所有权和取消路径；需要证明释放行为时运行页面进入/退出检查，记录设备、
  步骤与结果。无法运行时列为待验证，不把静态核对、编译或单测当成“无泄漏”证据。
- 注释、日志和 handoff 不得复制 PRD、operationGuidance、凭据或敏感正文。

## 分层构建验证

- Propose 为有构建影响的 change 指定一个集成验证节点及实际模块、variant、交付入口；日常 task
  只做与当前改动相关的静态检查或定向测试。已计划在后续集成验证的结果，明确记为“待集成验证”，
  不要求每次修改 XML/资源或 Kotlin/Java 后都运行 Gradle，也不能把轻量检查写成构建通过。
- 交付可运行页面、入口或跨模块接线时，在相关实施完成后构建实际应用
  `:<app>:assemble<Variant>`，通常每个交付变体一次；该命令成功已覆盖依赖模块的资源打包和代码编译，
  不必再重复执行单独的 `:<module>:package<Variant>Resources` 或 `compile<Variant>Kotlin`。
  库模块 AAR 不能替代 APK。没有可安装应用的变更只对受影响模块做必要的集成构建，并说明原因。
- 若整包构建暂不可行，或需要提前定位资源错误，可在集成节点运行实际执行 AAPT 的资源任务
  `:<module>:package<Variant>Resources`（无此任务时选等价任务），或定向模块编译；这是部分证据，
  不能称 APK 已通过。`xmllint`、`generate<Variant>RFile`、`compile<Variant>Kotlin` 均不能单独证明
  AAPT 通过。高风险改动可以提前运行定向验证，但不变成每个 task 的固定门槛。
- 使用完整 Gradle task 名，避免前缀匹配到其他变体或测试任务。缺依赖、网络权限或环境导致构建中断
  不能视为通过；按环境权限重试，仍失败则记录命令、变体、失败阶段和恢复条件，保持集成验证未完成。
  APK 构建与真机运行分别记录，不互相替代。

## UI 文本核对与视觉边界

- 对有 Figma 文本规格的 UI 复现，按 design 中选出的少量关键节点/状态检查运行中的实际页面。
  记录设备、密度、字号、主题、方向和 Insets；在可用环境中用 View 层级或 Compose 语义树等
  文本方式取得可观察的节点标识、父子关系、文案、状态和边界。只保留任务所需的脱敏差异，
  不把完整层级、真实业务数据或截图写进 handoff。
- 对比前确认设计数值的单位和运行时密度、坐标原点及系统栏影响；无法可靠换算时只比较层级或
  相对关系，不能把设备物理 px 与 dp 直接相减。项目若已确认当前页面按宽 AutoSizeConfig 适配、
  1× 设计画布宽与 `design_width_in_dp` 相同，可在适配坐标系对照设计尺寸/间距与同数值 dp；
  先在运行时复核页面实际适配与内容宽度。`design_height_in_dp` 和设计画布高度都不是运行时
  内容高度：记录实际可用高度与 Insets，核对设计是否含系统栏；高屏不强行拉伸，可用空间不足时
  才按需求滚动/重排，底部操作对齐安全区，不按 667/812 等比例压缩整页。以“页面/状态、节点、
  设计值及单位、运行值及配置、差异、未取得项”记录少量关键差异，不预排完整状态矩阵。
- 文本树可能缺少纯装饰节点、字体渲染、颜色、图标内容和动效；不能据此断言视觉一致。Agent 无法
  运行或无法取得关键节点时记录原因和待核对项，把必要的文本核对移入 `[人工]` 项，不绑在只负责
  构建的任务上，也不编造通过结果。需要视觉复现验收的页面保留独立
  `[人工]` 任务：人工自行对照设计与实际页面，给出页面/状态、设备配置、区域、预期与实际差异、
  通过或待改的文字反馈，不要求向模型上传图片。失败后修复并重新取得人工反馈，不以 APK 或节点
  文本核对替代视觉结论。
