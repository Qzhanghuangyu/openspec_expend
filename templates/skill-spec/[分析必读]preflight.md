# [分析必读] Preflight（需求分析）

## 目标

按独立的用户可观察行为核对当前实现、需求缺口和设计阻断项；正式 artifact 只产出 `preflight.md`，必要取证引用留在父 change 的 Agent 工作文件。

## 输入

- 用户提供的 PRD 或需求说明。
- 当前项目代码、接口、模型、测试和已有规格。
- 已有父 change 的 `prd-source.md`（若有在线 PRD 取证）及设计源引用。
- 可选：用户在当时对话明确提供的设计节点，或本 change 的 `design-source.md`。

## 必须执行

1. 读取完整需求；不可访问或范围不明时请求补充。飞书文档/Wiki PRD 还须读取评论和回复：

   ```bash
   lark-cli docs +fetch --doc "<PRD URL>" --scope full
   lark-cli drive +list-comments --url "<PRD URL>" --solved-status all --comment-scope all
   # 对每个 comment_id：
   lark-cli drive +list-replies --url "<PRD URL>" --comment-id "<id>"
   ```

   `reference_map.comments` 只辅助定位；沿 `--page-token` 读取全部评论和回复，区分解决状态、
   正文锚点、澄清与决策。
   记录正文版本和评论核对时间到父 change 的 `prd-source.md`；读取期间版本变化或用户指出评论更新时重新核对。
   评论接口无权限、失败或分页/截断未补齐时暂停，报告恢复条件，不声称没有评论。
   仅访问当前 PRD，不扩大到同一知识空间里的其他文档。
   先确定当前 Android 范围，将已确认的评论澄清并入对应需求项；“已解决”不等于已确认。
   未决、矛盾或无决策依据的建议不覆盖正文，按 `Decision Required` 或 `Conflict` 记录。
   将长评论 ID、位置、解决状态、回复完整性和精简取证结论只记入父 change 的 `prd-source.md`；
   `preflight.md` 仅用章节/问题主题描述已确认结论与未决事项，不复制机器 ID；不复制整段评论或个人信息。
   取证文件不是凭据仓库：不保存原始 URL、cookie、认证 token、回复全文或临时链接。
   按 Schema 模板创建取证文件，只接受项目内普通文件，不跟随符号链接；无在线 PRD 时不创建。
2. 执行 `openspec list --json`，优先复用同名或范围重叠的父 change。
3. 不存在可复用 change 时创建：

   ```bash
   openspec new change "<name>" --schema falla-spec-driven --goal "<goal>" --json
   ```

4. 获取官方写作指引：

   ```bash
   openspec instructions preflight --change "<name>" --json
   ```

5. 先按页面、区域或业务对象组织需求，再按下节拆出独立行为，记录触发条件、可观察结果和需求依据；
   已确认行为与有范围依据但尚未定义的行为缺口分别标明，不先用整页的实现状态替代拆分。
6. 只调查需求范围，以文件、符号、模型、接口或测试支撑每个行为的实现状态。
   区分可观察结果与实现建议；第三方 API 行为须核实，不凭名称推断。
   按“按需求事实核对”检查实际存在的对象、状态、事件和接口，记录必要缺口。
7. 按“单一决定与覆盖核对”分别记录待确认问题，反查完整 PRD 及适用评论，确认当前范围内的明确行为均已覆盖。
   每个问题标记 `Missing Definition / Conflict / Implementation Risk / Decision Required`，以及
   `Blocker / Major / Minor`，并说明具体阻断的 artifact 或实施决策；再维护现有 Blocker 台账。
8. 涉及授权设计节点时，必须读取 `references/design-tools.md`，按其中取证交接规则创建或更新父
   `design-source.md`；本阶段仅填必要的分析事实和缺口，不冒充完整设计。
9. 写入官方 `resolvedOutputPath`，运行 status 确认 preflight 为 `done`。
   按“阻塞项准入记录”维护准入台账；官方 done 只说明产物已生成，不证明 Blocker 已解决。
   用户答复阻塞问题后只更新当前 `preflight.md` 的结论与取证文件，复核 status 后结束本阶段；
   不以 Blocker 已解决或 proposal 就绪为由自动运行 Propose/Apply。

## 需求行为拆分

- 一条需求应能单独回答“要求什么、现在是否实现、如何判断”。同一功能中，触发条件、可观察结果或实现状态
  不同的行为分开记录，不能用“部分实现”笼统覆盖整页。
- 页面展示、默认选中、点击提交、成功反馈、失败反馈等有独立需求依据时分别分析；不按代码行、XML 属性或
  装饰图层拆项，不为增加条数拆出没有独立意义的内容。简单静态需求允许只有一项。
- 每项记录页面/对象、独立行为、触发与结果、需求依据、实现状态和证据。长证据或条件放在条目下，
  主表保留简短定位；只保存必要的脱敏结论和项目内证据，不复制 PRD 原文、业务数据或凭据。
- 状态使用已实现/部分实现/未实现/无法判断；同一独立行为的关键分支或契约未核实时写“无法判断”并说明核验缺口，
  不得仅因搜索不到就断言不存在。标为部分实现时仍须明确已有证据和缺失结果。
- 使用本 change 内稳定的 `R1`、`R2` 等编号关联分析条目；只用于正文追踪，不替代 tasks 的章节.序号，
  不新增独立台账文件或需求覆盖解析器。未定义的行为缺口须关联待确认问题，不当作已确认规格。

## 按需求事实核对

先识别本次需求内真实的对象、事件、状态与接口，再检查适用维度；已明确且已核实的内容只记简洁结论，不反复提问。

| 适用维度 | 核对内容 | 范围依据 |
| --- | --- | --- |
| 展示与入口 | 可见条件、内容来源、初始或默认状态 | PRD 明确的页面、区域或入口 |
| 状态与交互 | 事件、前后状态、状态来源及适用的持久化要求 | 实际存在的状态对象或交互 |
| 数据与接口 | 业务概念与字段、接口、错误码的映射 | 本次行为所需的数据契约 |
| 边界与异常 | 限制、并发或重复操作、失败等对验收的影响 | PRD、接口契约、平台硬约束或当前实现路径 |
| 兼容与生命周期 | 与旧行为的冲突，资源和回调的持有者及使用边界 | 受影响代码和已核实的工程约束 |

核对方法主干及接口或架构的硬性冲突；基于本次需求、已核实的接口契约、明确的平台约束或当前实现路径，
识别影响本次完成条件的必要边界。不套通用清单、不无限枚举，不预设生命周期或 NPE 检查清单；
这些维度用于检查覆盖，不要求每个功能都写五段。不涉及权限就不加权限问题，没有提交就不加重复提交问题。
新增功能没有源码也可依据上述范围事实识别缺口；缺少产品决定时记录为待确认，不补成已确认行为。
每项必要边界只记录范围依据、触发条件、缺少的决定、影响和待确认项；不自行选择默认值、重试、兜底、弹窗或降级方案。
Android 资源所有权、页面销毁后回调等可核实的工程约束按实际证据核对；
不把离开页面是否取消业务请求等不确定产品行为当作工程惯例。例如异步提交期间允许返回而离页后行为未定义时，
分别记录业务是否继续、结果如何反馈的决定缺口，并核对回调是否仍会更新已销毁 View；不自行规定取消或后台重试。

## 单一决定与覆盖核对

- 一个问题对应一个可独立答复的决定；不同决定分开记录，多个行为共享同一决定时关联多个 R 编号，不复制问题。
  Blocker 正文直接用现有 `B1` 等编号；Major/Minor 可用 `Q1` 等编号，不建立第二份决定状态台账。
- 问题记录关联行为、范围依据、触发条件、缺少的单一决定、影响、类型和级别。
  按具体阻断的 artifact 或实施决策定级；没有具体阻断的问题不一律列为 Blocker。
- 反查完整 PRD 及适用评论，将当前 Android 范围内的每项明确行为对应到差分条目；列出未覆盖或无法判断的项及原因，
  范围外内容只做简要定位，不重复生成其他端的完整需求分析。存在遗漏时先补条目，再结束核对。
- 已有记录不因缺少 R 编号而自动失效，不自动重写旧 preflight 或重编已开始的 tasks；续做时按实际需求变化补证据。
  已完成证据的影响复核及归档限制沿用“已实施后的需求修订”。覆盖由 Agent 核对、人工审阅；程序只检查现有格式和准入，
  不证明自然语言分析质量或行为覆盖完整性。

## 阻塞项准入记录

父 `preflight.md` 顶部使用 YAML frontmatter，作为当前 change 阻塞项状态的唯一事实源：

```yaml
---
falla-preflight: 1
reviewed: true
blockers:
  - id: B1
    scope: 默认选中行为，影响规格及任务完成条件
    status: pending
    decision: ''
    evidence: ''
---
```

- `reviewed` 为是否已经完整核对本次需求及阻塞项清单；核对完成才设 true，不代表用户已批准所有决定。
  未核对保持 false；只有核对后确实没有 Blocker 才可保留 `blockers: []`，不得为通过校验而清空台账。
- 每个 Blocker 使用唯一编号 B1、B2 等（B 后为 1–6 位正整数）、非空 `scope` 和明确 `status`。
  正文以编号关联问题、影响和建议确认项；Major/Minor 仍记正文，不强制全部提前解决。
  准入读取上限为文件 256 KiB、台账 256 项；超限、重复编号、无效 YAML 或别名均不放行，不截断后继续。
- `pending`：待确认，阻断当前 change 的 Propose 准入及 Apply 认领；不依赖该问题的只读调查可以继续。
- `confirmed`：已有明确决定；`decision` 写精简决定，`evidence` 写可追溯的用户答复或已核实的权威需求依据。
- `excluded`：用户明确排除本次范围；`decision` 说明排除范围，`evidence` 记录明确依据。
  不删除已排除的问题；下游规格和任务不得继续包含该范围。延期仍在本次范围内的问题不能标为 excluded。
- confirmed/excluded 的 decision/evidence 都必须非空；不得把猜测、“继续”、调用 Skill、沉默或评论已解决当成确认。
  不保存完整对话、原始链接、个人信息或凭据。程序只校验格式、状态与依据存在，Agent 必须核实依据内容真实有效。
- 不从自然语言里的“无问题”或 Blocker 数量推断准入；缺少字段的旧 change 显示未核验。
  显式核对原文与既有决定后再补台账，不自动改写旧结论；已归档记录不原地补写，需要恢复工作时新建 change。
- 只读检查命令：`falla-openspec coordination preflight "<parent>" --json`。
  `preflight-unverified` 表示需核对补齐；`preflight-invalid` 表示结构无效；`preflight-blocker-unresolved`
  表示仍有待确认项；`preflight-decision-evidence-required` 表示决定或依据缺失；`preflight-unreadable` 表示安全读取失败。
  任何一种错误都不得按准入通过处理；仅反馈问题编号和恢复条件，不回显敏感正文。

## 已实施后的需求修订

未归档 change 的已确认决定、PRD 范围或验收条件改变时，更新台账不得保留旧需求的默认批准。
先核实冲突和用户决定；已有完成/人工证据时加载 coordination 的“实施基线与完成证据失效”，列受影响范围，
交回 Propose 修订及各 owner 回退。不自动清空任务、不重建 comate，不把修订后的 preflight done 当作旧证据仍有效。
归档内容使用新 change，不原地改写。

## 何时暂停

- PRD 不完整或不可访问；飞书 PRD 的评论/回复因权限、截断或分页失败而无法核对。
- Blocker 会阻止 proposal、spec、design 或任务拆解。
- 结论只能依赖猜测，无法获得当前代码或接口证据。

未阻断后续决策的问题继续记录在 preflight 中，不要求全部提前解决。

## 完成标准

- `preflight.md` 有明确结论，包括无问题时。
- 当前范围内的明确行为均有差分条目，触发、结果与需求依据可核对；未定义的行为缺口与已确认行为区分，
  无法判断和明确排除的范围有说明，不用整页的部分实现掩盖独立行为差分。
- 每个实现状态都有证据或明确的核验缺口，每个问题只有一个待答复决定并关联行为，具有类型、级别、影响和建议确认项；飞书 PRD 记录评论
  读取范围、已解决/未解决状态、对正文的影响和未决争议。
- 未创建其他正式 artifact 或子 change；取证文件仅含最小定位信息，不写凭据或评论全文。
- 未修改业务代码、构建配置或测试。
- 已反馈剩余阻塞项和下一阶段可否进入；停在 Preflight，等待用户手动发起 Propose。
